# 공부: 두 발 로봇 기초 개념

> 2026-11-04에 만든 팀 설명 슬라이드("오리 로봇, 이해부터 4주 실행까지")의 기초 이해 부분을 문서로 옮겼다. 로봇을 처음 보는 팀원이 **오또봇 1단계를 시작하기 전에** 읽는다. 오또봇에서 직접 확인할 수 있는 부분은 ▶ 로 표시했다.

## 1. 몸체 · 감각 · 판단 · 움직임

| | 역할 | Open Duck Mini | 오또봇 (1단계) |
|---|---|---|---|
| 01 기구 | 몸통 · 다리 · 관절 힘을 버티는 구조 | 3D 출력물 51개 | 3D 출력물 6개 |
| 02 센서 | 관절 각도 · 기울기 등 현재 상태 측정 | BNO055, 발 스위치, 모터 위치 | 6축 IMU |
| 03 컴퓨터 | 상태와 명령을 보고 다음 자세 결정 | Raspberry Pi + 정책 | NU40 + 사인파 |
| 04 모터 | 목표 각도로 움직여 몸을 지지 | STS3215 14개 | SG90 4개 |

**상태 측정 → 목표 계산 → 모터 구동 → 다시 측정.** 부품 이름보다 이 순환을 먼저 기억한다. 걷기는 정해진 각도를 한 번 보내고 끝나는 일이 아니다. 몸이 흔들리는 동안 센서를 읽고 자세를 계속 바꿔야 한다.

점검도 같은 순서로 나눈다. 기구가 걸리지 않는지 → 센서가 맞는지 → 계산 결과와 모터 명령이 맞는지 각각 확인하면 원인을 좁힐 수 있다.

## 2. 서보모터와 관절 영점

- 서보는 **목표 위치**를 받아 움직인다. 버스 서보(STS3215)는 현재 위치도 읽을 수 있다. PWM 서보(SG90)는 읽을 수 없다.
- **ID**는 모터 주소, **영점**은 각도 계산의 기준이다.
- 작은 설정 오류가 몸 전체에 영향을 준다: 좌우 모터 주소가 뒤바뀜, 서 있는 기준 각도가 틀림, 회전 방향이나 관절 순서가 다름.
- 정책이 "왼쪽 무릎"에 명령했는데 오른쪽 발목이 움직이면 모델이 아무리 좋아도 제어할 수 없다. **숫자의 순서와 부호도 주소만큼 중요하다.**
- 모터 한 개의 ID · 방향 · 위치를 확인한 뒤 전체로 넓힌다. 관절별 ID · 설정값 · 보정값을 표로 남기면 재조립 · 교체 때 시간을 아낀다.

▶ 오또봇: 웹 컨트롤러의 **트림**이 영점 맞추기다. `SERVO_REVERSE`가 방향, `SERVO_PINS` 순서가 관절 순서다.

## 3. 전원과 통신은 다른 역할

| | 뜻 | 주의 |
|---|---|---|
| 전압(V) | 부품이 요구하는 범위에 맞춘다 | 같은 모터 계열도 전압 · 기어비가 다르다. 판매 제목만 보고 대체품을 고르지 않는다 |
| 전류(A) | 부하가 요구한다 | 여러 모터가 힘을 쓰면 순간 요구량이 커진다 |
| 통신 | 컴퓨터가 "어느 모터를 어디로" 전달하는 경로 | USB가 연결됐다고 모터 전원까지 준비된 것은 아니다 |

전원이 불안정하면 컴퓨터 재부팅, 모터 힘 부족, 통신 오류처럼 보인다. **통신 문제를 디버깅할 때도 전원을 같이 본다.** 배선 · 전원은 경험자의 검토를 받고, 새 배터리 회로 설계는 초기 범위에서 뺀다.

▶ 오또봇: 서보 전원을 보드와 분리하고 GND만 묶는 이유 ([02-하드웨어](02-하드웨어.md) 3절).

## 4. IMU와 좌표계

| 축 | 뜻 |
|---|---|
| Roll | 좌우로 기울어짐 |
| Pitch | 앞뒤로 숙여짐 |
| Yaw | 좌우로 방향 전환 |

IMU는 회전 속도와 가속도를 잰다. 프로그램은 이걸로 자세를 추정하거나 중력 방향을 계산한다. **센서를 붙인 방향과 프로그램의 방향 기준이 맞아야 한다.** 반대로 달았는데 그대로 읽으면 기울기를 거꾸로 해석한다.

처음에는 쿼터니언 수식을 다 이해하기보다, 손으로 로봇을 앞 · 뒤 · 좌 · 우로 조금씩 기울이고 화면 값이 예상대로 바뀌는지 확인하는 게 중요하다.

▶ 오또봇: 웹 상태 칸의 "앞뒤 기울기 / 좌우 기울기"로 바로 해 볼 수 있다. 축이 다르면 `imu.h`의 `IMU_AXIS_*` · `IMU_SIGN_*`을 고친다.

## 5. 정책은 다음 동작을 고르는 모델

```
현재 상태(기울기, 관절 위치 · 속도) + 사람의 명령(앞으로, 고개 돌리기)
        → 정책(학습된 모델) → 모터 목표(각 관절을 어느 위치로)
```

- "앞으로 가"는 고수준 명령, 무릎 · 발목 목표값은 그걸 실현하는 저수준 출력이다.
- Open Duck Mini · Microduck 실행 구조는 **50Hz** — 1초에 50번, 약 20ms마다 반복한다.
- 정책 파일만 있으면 끝이 아니다. **관절 순서 · 입력 형식 · 보정값**까지 맞아야 한다. 다른 로봇용 정책을 확장자(ONNX)가 같다는 이유로 넣으면 안 된다.

▶ 오또봇: 정책 대신 사인파가 50Hz로 관절 목표를 낸다 (`gait.h`). TinyML 자세 분류도 "입력 → 작은 신경망 → 출력" 구조라 정책과 같은 흐름을 작게 연습한다.

## 6. 기존 정책 실행 vs 새 정책 학습

| | 기존 정책 실행 | 새 정책 학습 |
|---|---|---|
| 하는 일 | 만들어진 동작 모델 사용 | 가상 시행착오로 모델 개선 |
| 핵심 작업 | 설치 · 입력 · 모터 · 센서 맞추기 | 관측 · 행동 · 보상 설계 |
| 주요 변수 | 설정과 실제 기구의 차이 | GPU · 학습 비용 · 검증 시간 |
| 첫 실물 단계 | **우선** | 이후 |

강화학습은 로봇이 보는 정보(**관측**), 할 수 있는 움직임(**행동**), 잘했는지 평가하는 점수(**보상**)를 정의한다. PPO는 정책을 개선하는 알고리즘 중 하나다. 새 학습을 시작하면 설치 · 실험 · 평가 · 실물 이전까지 일이 크게 늘어난다. **처음엔 공개 정책을 정상 실행하는 것이 먼저다.** 머리 명령을 조합한 인사처럼 새 학습 없이 되는 기능이 있는지 먼저 본다.

## 7. 가상에서 되던 동작이 실물에서 흔들리는 이유 (sim2real)

| 가상과 다른 점 | 실물에서 보이는 현상 | 먼저 확인할 것 |
|---|---|---|
| 관절 영점 · 센서 방향 | 한쪽으로 계속 기울어짐 | 서 있는 기준과 IMU |
| 모터 힘 · 속도 · 기어 유격 | 발을 충분히 못 들거나 흔들림 | 정확한 모델 · 체결 상태 |
| 전원 · 통신 지연 | 부하 시 불안정, 반응이 늦음 | 전압과 제어 주기 기록 |

표는 가능한 원인의 예시이고 진단 규칙이 아니다. **한 번에 조건 하나만 바꾸고, 바꾸기 전후를 같은 시험으로 비교한다.**
Microduck 학습 자료는 전압 · 마찰 · 지연을 바꾸는 도메인 랜덤화와 모터 모델을 설명한다. 원리는 참고하되 **Microduck 파라미터를 Open Duck에 그대로 쓰면 안 된다.**

## 8. 용어 사전

| 용어 | 쉽게 말하면 | 필요한 깊이 |
|---|---|---|
| 정책 / 추론 | 동작을 고르는 모델 / 모델을 실행하는 일 | 불러오기 · 입력 · 출력 이해 |
| MuJoCo | 가상 로봇과 접촉 · 물리를 계산하는 도구 | 예제 실행 · 관찰 |
| ONNX | 학습된 모델을 실행 환경으로 옮기는 파일 형식 | 해당 로봇용 파일 고르기 |
| IMU / 영점 | 기울기 · 회전 센서 / 관절 각도의 기준 | 방향과 기준 검증 |
| Git / 커밋 | 변경 기록 도구 / 특정 시점의 버전 | 작동 버전 고정 · 복구 |
| PPO / 보상 | 정책 학습 알고리즘 / 행동을 평가하는 점수 | 지금은 개념만 |
| TinyML | 마이크로컨트롤러에서 돌리는 아주 작은 모델 | 1단계에서 직접 해 봄 |
| STL / G-code | 3D 모양 파일 / 특정 프린터용 실행 지시 파일 | 다른 프린터용 G-code를 그대로 쓰지 않기 |

가장 중요한 세 가지: **학습은 실행보다 무겁다. 같은 ONNX라도 로봇과 입력 형식이 다르면 호환되지 않는다. 가상 성공은 실물 성공이 아니다.**
처음부터 모든 수학을 배우기보다, 지금 막힌 문제를 설명할 만큼 공부한다.
