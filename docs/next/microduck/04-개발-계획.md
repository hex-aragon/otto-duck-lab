## 1단계: 공식 학습 재현

먼저 아무것도 바꾸지 말고 그대로 돌린다.

```bash
git clone https://github.com/pollen-robotics/microduck_rl
cd microduck_rl
hf auth login
wandb login

# 그래픽카드 없는 환경: 먼저 --dry-run으로 작업 내용만 확인
uv run train Mjlab-Velocity-Flat-MicroDuck --env.scene.num-envs 4096 --hf-jobs --dry-run
uv run train Mjlab-Velocity-Flat-MicroDuck --env.scene.num-envs 4096 --hf-jobs --timeout 3h

# 결과 내보내기, 키보드로 시험
uv run scripts/export.py Mjlab-Velocity-Flat-MicroDuck --wandb-run-path <경로>
uv run scripts/infer_policy.py --walking output.onnx
```

- [ ] 요금 확인 후 첫 학습 실행
- [ ] 보상 곡선 읽는 법 익히기
- [ ] 내 PC(CPU)에서 키보드로 걷게 하기

`uv run`, `hf`, `wandb`는 미리 설치가 필요할 수 있다. 내 WSL 메모리가 3GB로 잡혀 있어 설치나 빌드 때 부족하면 WSL 메모리 설정을 늘린다.

## 2단계: 내 동작 만들기

**첫 목표 후보: 박자에 맞춰 머리와 몸을 흔드는 "음악 오리".** 걷기처럼 넘어질 위험이 작으며, 움직임 결과를 눈으로 평가하기 쉽다.

1. 머리 명령을 바꾸는 것부터 시작한다. 모든 정책이 머리 · 몸 자세 명령을 받으므로 새 학습이 필요 없을 수도 있다.
2. 부족하면 비슷한 과제를 복사해 보상을 고친다.
3. 도메인 랜덤화는 끄지 않는다. 실물로 옮기기 위해 필요하다.
4. 형식이 맞는지 확인하고 Hugging Face에 올린다.

```bash
uv run publish    # microduck_rl에서 규격에 맞는 정책 저장소 만들기
```

저장소 이름은 `<사용자>/microduck-<이름>`, 파일은 `policy.onnx`와 `manifest.json`이며 입력 61 · 출력 14여야 한다. 자세한 인자는 저장소 문서에서 확인한다.

**완료 기준:** 무작위 조건 여러 번에서 넘어지지 않고 동작을 끝낸다.

## 3단계: 로봇 프로그램을 시뮬레이션에서 실행

실제 로봇 프로그램을 가상 몸체에 붙이는 단계다. 실물 없이 명령 사용법을 전부 익힐 수 있다.

```bash
git clone https://github.com/pollen-robotics/microduck
# microduck_rl을 옆에 두고 가상 환경 준비
cd microduck
cargo build
scripts/duck-sim                     # 오리 1마리 실행
scripts/duck-sim status
scripts/duck-sim drive               # 8초 전진
scripts/duck-sim monitor             # 관절 · IMU · 거리 센서
scripts/duck-sim ctl policy add <이름> <저장소>
scripts/duck-sim down
```

- [ ] WSL에서 동작하는지 확인. 화면 표시 · 시스템 도구 문제가 있을 수 있고, 안 되면 Linux 전용 환경을 검토 `TODO: 확인 필요`
- [ ] 실시간 배율 1.0 이상 확인. 낮으면 정책이 넘어진다
- [ ] 내 정책을 스킬로 설치해 실행

시뮬레이션에는 실제 모터 통신, 블루투스, 카메라 처리, NPU가 없다. 그 부분의 문제는 실물에서만 나타난다.

## 5단계: PC에서 오리 조종 (UDP 패드)

공식 네트워크 게임패드 기능을 쓰면 로봇 코드를 고치지 않아도 된다.

```
[키보드 · 웹 컨트롤러] → [PC 파이썬 중계기] → UDP 4210 → [netpadd] → 오리
```

브라우저는 UDP를 직접 보낼 수 없으므로 작은 파이썬 중계기가 필요하다. 로봇의 블루투스 경로는 설계 문서상 설정 · 상태 조회 등 일부 기능만 열려 있어서 UDP를 쓴다.

**패킷 형식 (28바이트, 공식 문서 `udp-pad.md`)**

```python
import struct
packet = struct.pack(
    "<4sBBII6hH",
    b"DKPD", 1, 0, seq, t_ms,
    lx, ly, rx, ry, lt, rt,   # 스틱 ±32767, 트리거 0~32767
    buttons,
)
```

**작업 목록**

- [ ] 파이썬으로 키보드 입력 → 패드 값 변환 (오또봇 웹 컨트롤러의 W A S D 홀드 방식과 같게)
- [ ] UDP 패킷 전송 (초당 30번. 300ms 끊기면 로봇이 멈춤)
- [ ] 가상 오리에서 `netpad.enabled = true`로 시험. 가상 환경 지원 여부 `TODO: 확인 필요`
- [ ] 안전 처리: 입력 끊김 시 전송을 멈춤, 전원 끄기 버튼은 보내지 않음, 값 범위 제한
- [ ] 데드존은 로봇이 처리하므로 중계기에서 넣지 않음

## 7단계: 실물 도착 후

1. 기본 동작 7종을 게임패드로 확인한다.
2. 시뮬레이션 값과 실제 값을 비교한다. 저장소의 `scripts/testbench_sim2real.py` 참고.
3. 낮은 속도의 내 걷기 정책을 푹신한 바닥에서 시험한다. 손으로 받칠 준비를 한다.
4. 안 되면 원인을 지연, 모터 모델, 기어 유격 순서로 살핀다. 기어 유격 학습 변형(`-Backlash`)이 있다.
5. 정상 동작 후 오또봇에서 만든 넘어짐 감지 · 웹 조종, 카메라 · 거리 센서 활용으로 넓힌다.

## 위험과 대응

| 위험 | 대응 |
|---|---|
| 배송이 더 늦어짐 | 1~6단계는 실물 없이 진행하도록 짰다 |
| 클라우드 비용 증가 | 타임아웃 짧게, 환경 수 조절, 첫 실행은 `--dry-run` |
| 가상에서만 되고 실물에서 안 됨 | 랜덤화 유지, 동작을 작게 시작, 7단계 순서로 원인 찾기 |
| WSL에서 시뮬레이터 실행 실패 | 학습은 클라우드라 영향 없음. 3단계만 별도 환경 검토 |
| 소프트웨어 변경이 잦음 | 작은 단계마다 사용한 커밋을 기록 |
| 모터 고장 · 과열 | 개발 팩의 예비 모터, 시험 시간 제한, 온도 확인 |
